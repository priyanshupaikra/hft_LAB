# learning.md — hft-lab explained end to end

This document explains **what the system does, why it exists, how an order
flows through it, and which data structures power each part** — with the
classic interview problem each structure maps to. Read it next to the code;
every section names the file it describes.

---

## 0. Purpose — why build an exchange?

Three goals, in priority order:

1. **Learn system design as a *trading system*, not as abstract boxes.**
   Rate limiting, idempotency, circuit breakers, caching, sharding — these
   concepts were born in finance infrastructure decades before web apps
   popularized them. Building them in their native habitat (order flow)
   makes them stick.
2. **Learn the C++ that HFT interviews test.** The hot path is pure C++20
   stdlib: ordered maps, lists, hash maps, atomics, fixed-point math,
   steady-clock timing. Every choice is one you can defend in an interview
   ("why a map here and not a heap / vector / unordered_map?").
3. **Have one portfolio artifact that tells a story.** "I built a matching
   engine that does ~8-12M orders/sec single-threaded, fronted by a gateway
   with a kill switch that auto-trips on fat fingers, and a Python injector
   that proves it live" — that sentence opens doors at Citadel, Tower, HRT,
   Jump. Jane Street mostly wants to watch you think; this repo is the
   thinking you'll do together.

The deliberate split — **C++ for the venue, Python for the tooling** —
mirrors real firms: trading infrastructure in C++, research/ops tooling in
Python.

## 1. What the system does (plain English)

hft-lab is a **simulated stock exchange with a safety-conscious front
door**. It is three programs talking over TCP:

| Program | Language | Role |
|---|---|---|
| `hft_gateway` | C++ | The exchange: accepts connections, checks every order for safety, matches buyers with sellers, reports fills and stats |
| `py/injector/injector.py` | Python | A fake client: sends orders at a controlled rate, can send duplicates and fat-finger mistakes on purpose |
| `py/monitor/monitor.py` | Python | An ops dashboard: polls `STATS` and prints counters, latency percentiles, and the kill-switch state |

What happens functionally: a client connects, logs in with a token, and
sends lines like `NEW 3 B 5 10050` — "buy 5 shares at $100.50". The gateway
decides whether that order is *allowed* (identity, rate, duplicates, risk),
then either **rests it on the order book** (parked, waiting for a
counterparty) or **matches it immediately** against the opposite side
(generating a fill/trade). Clients can cancel resting orders, pull their
maker-side fill notifications, and query stats. An admin can trip or reset
the kill switch; enough fat-finger rejections trip it automatically.

Nothing here touches real money or real markets — but the *shape* of every
component is the shape used in production trading systems.

## 2. The trading domain in 90 seconds

| Term | Meaning |
|---|---|
| **Bid / Ask** | Best price a buyer will pay / seller will accept. Best bid < best ask normally (the *spread*). |
| **Limit order** | "Buy 10 @ ≤ $99.50" — parks on the book if it can't trade immediately. |
| **Market order** | "Buy 10 at whatever the best price is" — never rests; leftovers are cancelled (IOC = immediate-or-cancel). |
| **Maker / Taker** | The resting order that provided liquidity is the *maker*; the incoming order that crossed the spread is the *taker*. Trades print at the **maker's** price. |
| **Price-time priority** | Best price trades first; at equal price, the order that arrived first trades first (FIFO). |
| **ClOrdID** | Client-assigned order ID. If the network retries a message, the exchange must not double-trade — that's what idempotency keys are for (FIX protocol: `ClOrdID` / `PossDupFlag`). |
| **Fat finger** | A typo'd price or quantity (sell 1M shares at $1 instead of 1 share at $1M). Pre-trade risk exists to bounce these. |
| **Kill switch** | The big red button: reject all order flow. Regulators and exchanges effectively require one; here it's a proper circuit breaker. |
| **Fill** | An execution: quantity traded at a price between a maker and a taker. |

## 3. End-to-end order flow (follow one order)

`NEW 3 B 5 10050` typed by a client (or generated by the injector):

```
 Python injector                        C++ gateway process
 ───────────────                        ────────────────────────────────────────────────
 send "NEW 3 B 5 10050\n"  ──TCP──▶  server.cpp: recv() into per-conn buffer
                                         │  split buffer on '\n' → one command
                                         ▼
                                       parse (build_command)
                                         │  AUTH already done? (slot leased?)
                                         │  parse: cl=3 side=B qty=5 px=10050
                                         ▼
                                       push Command into session's SPSC ring
                                         │  (connection thread now parks on the
                                         │   response ring's condvar)
                                         ▼  ────── engine thread ──────
                                       TradingCore::process()
                                         │
                                         │  1. lease valid?            ── else ERR NO_SESSION
                                         │  2. kill switch allows?     ── else ERR KILL_SWITCH
                                         │  3. token bucket consume?   ── else ERR RATE_LIMITED
                                         │  4. ClOrdID unseen?         ── else ERR DUPLICATE
                                         │  5. qty/price/notional ok?  ── else ERR RISK_*
                                         ▼
                                       MatchingEngine::submit()
                                         │  assign engine order id, route by symbol
                                         ▼
                                       OrderBook::submit()
                                         │  sweep asks_ while price crosses
                                         │  ├─ match maker at front of level → Fill
                                         │  ├─ maker exhausted? erase, else stop
                                         │  └─ level empty? erase level
                                         │  remainder? rest on bids_ at back of level
                                         ▼
                                       fills → maker notifications to owner's ring
                                       top moved? → MdUpdate ring → publisher thread
                                         │
 response line ◀──TCP────────────────  pop Response, write to socket ("OK NEW ...")
                                         │
 (later) "EVENTS" ◀── maker polls ──    session event ring drained
```

Step-by-step commentary, with the check order explained:

1. **Parse** (`server.cpp`) — bytes arrive in arbitrary chunks; a leftover
   buffer accumulates until `\n`. This is the classic stream-framing problem
   (TCP gives you bytes, not messages).
2. **Check 1 — identity** (`trading_core.cpp`): the connection authed with a
   token that maps to a `TraderProfile` (`session.hpp`). AuthN = who;
   AuthZ = the limits attached to that profile.
3. **Check 2 — kill switch**: a global gate. Risk stops everything; it is
   deliberately *before* the rate limiter so a hard stop can't be drowned in
   traffic.
4. **Check 3 — rate limit**: per-session token bucket. If empty, reject. A
   rejected order consumes nothing — rejecting must be free, or attackers
   use rejections as a weapon.
5. **Check 4 — idempotency**: have I seen ClOrdID 3 from this session? If
   yes, `ERR DUPLICATE` — the retry of a request must never double-trade.
6. **Check 5 — risk**: qty within the profile cap; price sane; `qty × price`
   within the notional cap. Violations count toward the kill switch.
7. **Engine** (`matching_engine.cpp`): assign an engine order ID, find the
   book for the symbol (hash lookup — this is the seed of sharding).
8. **Book** (`order_book.cpp`): the sweep loop (next section). Returns fills
   and a status: `FILLED` / `PARTIAL` / `RESTING` / `IOC_CANCELLED`.
9. **Respond & notify**: the taker gets fills inline in the ACK; the *maker*
   (a different session, usually) gets an event queued that it picks up by
   polling `EVENTS`.
10. **Measure**: `now_ns()` at entry and exit of `submit()` feed the latency
    histogram, visible in `STATS` as `core_lat_p50_ns` etc.

## 4. Component deep dives (with the DS reasoning and interview problems)

### 4.1 Order book — the heart (`cpp/engine/order_book.{hpp,cpp}`)

**What it does.** Holds all resting limit orders for one symbol so that:
best price is found instantly, same-price orders trade in arrival order, any
order can be cancelled in O(1), and an incoming order can sweep multiple
price levels.

**The data structures.**

```cpp
std::map<Price, OrderList, std::greater<Price>> bids_;  // best bid = begin()
std::map<Price, OrderList>                 asks_;       // best ask = begin()
std::unordered_map<EngineOrderId, Locator> locate_;     // O(1) cancel
// OrderList = std::list<RestingOrder>  — FIFO per price level
```

**Why each choice:**

- `std::map` (ordered, O(log P)): you constantly need "the best price" and
  "the next-worse price" — that's ordered-container territory, and
  `begin()` is O(1). A hash map can't answer "next price above X". A sorted
  vector pays O(P) mid-insert (fat levels shifting). A binary heap can't
  cancel efficiently or enumerate levels for a sweep.
- `std::list` per level: append at back = arrival order = time priority,
  for free. Crucially, **erasing one element doesn't invalidate iterators to
  others** — which is what makes O(1) cancels possible with a locator map.
  A `deque`/`vector` would invalidate on erase from the middle.
- `locate_` hash map: order ID → (side, price, list iterator). Cancel is:
  hash lookup → erase list node → maybe erase empty level. O(1) average.

**The matching sweep (the algorithm to be able to write on a whiteboard):**

```
while remaining > 0 and opposite side has levels:
    level = best level of opposite side
    if limit order and price no longer crosses level: break
    for each maker at this level (front first = oldest):
        trade_qty = min(remaining, maker.qty)
        record Fill(price=level.price, qty=trade_qty, maker, taker)
        remaining -= trade_qty; maker.qty -= trade_qty
        if maker.qty == 0: erase maker (+ locator entry)
        else: break            # maker absorbed everything left
    if level empty: erase level
if remaining > 0:
    market order  -> IOC_CANCELLED (never rests)
    limit order   -> rest at back of my price level
```

Trades print at the **maker's** price — the taker crossed the spread, so
the maker's quote is the honest one.

**Complexity.** Submit: O(log P) to find/insert the level + O(F) fills
generated. Cancel: O(1) average. Best price: O(1). P = distinct price
levels (hundreds, not millions) — which is why `map` beats fancier
structures here in practice.

**Classic problems this maps to:**
- **LeetCode 1801 — Number of Orders in the Backlog**: literally this
  matching loop with two heaps. Know why heaps work there (no cancels) and
  why a real book needs maps+lists (cancels!).
- **LC 295 — Find Median from Data Stream**: the "two sides of a book" as
  two heaps; the dual-priority intuition.
- **LC 716 — Max Stack / LC 155 — Min Stack**: "pop the best, but also
  delete arbitrary elements" — the exact tension `map + list + locator`
  resolves.
- **Design question**: "Design a limit order book" — answer with the three
  structures above and the sweep loop.

### 4.2 Matching engine (`cpp/engine/matching_engine.{hpp,cpp}`)

**What it does.** Owns one `OrderBook` per symbol, assigns engine order
IDs, keeps stats (accepted/fills/qty_traded/resting), and remembers which
symbol each live order is on (for cancels).

**Data structures:** `unordered_map<SymbolId, OrderBook>` (routing),
`unordered_map<EngineOrderId, SymbolId>` (cancel routing),
`unordered_map<SymbolId, Price>` last-trade per symbol.

**Why it matters for system design:** two symbols never interact, so their
books can live on different cores or machines with zero coordination.
That's **sharding by instrument** — the same insight Kafka uses for
partitions. Phase 4 (ROADMAP) turns this hash map into N processes behind a
consistent-hash router.

**Classic problems:** LC 1396 (Design Underground System — per-entity state
in hash maps), LC 380 (Insert/Delete/GetRandom O(1) — hash-map-backed
collections).

### 4.3 Rate limiter — token bucket (`cpp/common/token_bucket.hpp`)

**What it does.** Each session owns a bucket with `burst` tokens, refilled
at `rate` tokens/sec. An order consumes one token; an empty bucket rejects.

**Why token bucket over the alternatives:**
- *Fixed window* ("100/min"): lets 200 through straddling a window
  boundary — the boundary-double-spend bug.
- *Sliding window log*: exact but stores every timestamp — unbounded memory.
- *Sliding window counter*: good approximation, still coarser.
- *Token bucket*: O(1) memory, O(1) check, and **allows controlled bursts**
  — which is what you want for trading (a legit strategy may burst at the
  open; you still want the sustained-rate cap).

Implementation detail: refill is computed lazily from elapsed time
(`tokens += elapsed_s * rate`, capped at burst) — no timer thread, no
drift.

**Where the demo proves it:** `./scripts/demo.sh` step 2 pushes 2000
orders/s against a 400/s limit (burst 800) and gets exactly the excess
rejected (`rate_rej` in STATS).

**Classic problems:** **LC 362 — Design Hit Counter** (the sliding-window
sibling of this), LC 359 — Logger Rate Limiter (dedupe + window). System
design: "add rate limiting to an API" — discuss all four algorithms and
when bursts are legitimate.

### 4.4 Idempotency — ClOrdID dedupe (`cpp/gateway/dedupe_window.hpp`)

**What it does.** Per session: "have I seen this ClOrdID recently?" — with
zero allocations and O(1) amortized cost.

**The structure:** an open-addressing hash table (linear probing) where
every slot is **generation-tagged**. "Clearing" the table = bumping the
generation, O(1), no per-entry deletion (the part that normally makes open
addressing awkward). A ClOrdID stays remembered across two generation bumps
(~1.5x table capacity of later inserts) — retries arrive milliseconds after
the original, so a window of thousands of recent IDs is far beyond any
sane retry behavior. Bounded memory beats perfect recall.

**Why:** networks retry; clients crash and resend; a duplicated "buy"
message must trade once, not twice. FIX solved this decades ago — ClOrdID
is the idempotency key, duplicates carry PossDup. In web terms this is why
payment APIs ask for an `Idempotency-Key` header.

**Classic problem:** **LC 146 — LRU Cache** (the memory-bound idempotency
structure this replaces); LC 706 — Design HashMap (you wrote one, with
generations).

### 4.5 Kill switch — circuit breaker (`cpp/gateway/kill_switch.hpp`)

**What it does.** A three-state machine gating ALL order flow:

```
        8 risk-rejects in 5s window                cooldown elapses
CLOSED ────────────────────────────▶ OPEN ─────────────────────────▶ HALF_OPEN
  ▲                                   ▲                                 │
  └──── 50 clean orders in probation ──┴── any risk reject in probation ┘
        (closes breaker)                    (re-trips with 2x cooldown)
```

- **CLOSED**: business as usual; risk rejections are timestamped into a
  deque window (drop entries older than 5s — a *sliding window* over
  events).
- **OPEN**: everything gets `ERR KILL_SWITCH`. Lasts `cooldown` (10s base,
  doubling on re-trips — exponential backoff, same idea as TCP retries and
  retry-after-429).
- **HALF_OPEN**: probation. 50 clean orders close it; one violation re-trips.
- **Admin override**: `KILL` / `RESUME` force states — the human button.

Time is injected as a parameter to every call, so the unit tests
(`kill_switch_auto_trip_and_recover`) fast-forward through a whole
trip/recover cycle in nanoseconds instead of sleeping 20 real seconds.
That trick (clock as dependency) is worth stealing for all your state
machines.

**Why it's the most literal concept mapping:** trading's kill switch
predates the "circuit breaker" pattern in web services by decades; Resilience4j
/ nginx circuit breakers are this exact state machine.

**Classic problems:** state machines everywhere (LC 8 — String to Integer
is a famous FSM exercise); sliding window over events (LC 239 family);
"design a retry with exponential backoff + jitter" (system design follow-up:
why jitter? — thundering herd).

### 4.6 Latency histogram (`cpp/common/histogram.hpp`)

**What it does.** Records nanosecond latencies and answers percentiles —
with **fixed memory and O(1) record**, no allocation on the hot path.

**How:** log2 bucketing — a 250ns sample lands in bucket
`64 − countl_zero(250)` = bucket 8 (range [256, 512)). Counters are
`std::atomic` (relaxed ordering — we're counting, not synchronizing).
Percentile = walk buckets to the target rank, linearly interpolate inside
the bucket. It's a coarse cousin of **HdrHistogram**, which real trading
telemetry uses.

**Why not store-and-sort?** A server that buffers every sample to compute
exact percentiles eventually dies of its own telemetry. Fixed memory beats
exact percentiles for dashboards. (The *benchmark binary* does use exact
vector+sort — offline analysis can afford it.)

**Classic problems:** bucket/count-based aggregation = counting sort
intuition (LC 274 H-Index does exactly this trick); LC 347 Top K Frequent;
"why p99 and not average" (averages hide tail latency — the tail is where
the money dies in trading).

### 4.7 Server, sessions, event queues (`cpp/gateway/server.{hpp,cpp}`, `trading_core.hpp`)

**What they do:**
- **Server**: blocking accept loop; one thread per connection; `TCP_NODELAY`
  (latency over throughput — disable Nagle); per-connection leftover buffer
  for framing. Connection threads are deliberately dumb: parse a line, push
  a `Command` into the session's SPSC ring, wait for `Response`s, write
  them to the socket. No trading logic, no state.
- **Sessions**: preallocated *slots* (fixed array of 64). Each slot: two
  SPSC rings (in/out) + a parking condvar for the client thread.
- **Event queue = producer/consumer**: the engine produces fill
  notifications into a fixed ring; the owning session consumes them when it
  sends `EVENTS`. That's the *polling* shape; the MD stream (§4.9) is the
  *push* shape. Both in one repo = the webhooks-vs-polling lesson embodied.

**Classic problems:** LC 622 — Design Circular Queue (this *is* one, with
atomics); producer-consumer with condition variables (OS classic).

### 4.8 The lock-free hot path (`cpp/transport/spsc_queue.hpp`, `trading_core.{hpp,cpp}`)

**The architecture change (the Phase 3 story):** before, every connection
thread grabbed one mutex and ran the whole pipeline inline — correct, but
contended, and the engine's state was touched by everyone. Now: each
session owns two SPSC rings; **one engine thread** drains them and owns
*all* trading state (books, kill switch, buckets, dedupe, counters). The
order path takes no locks at all.

**The Vyukov SPSC design — the memory-ordering contract:**
- `tail_` written only by the producer, `head_` only by the consumer
  (single-writer per variable is what makes this lock-free-simple).
- Producer: load tail **relaxed** (only we write it) → if maybe-full,
  reload head **acquire** (see consumer progress) → write slot → store tail
  **release** (publish slot contents before the index).
- Consumer: mirror image.
- Each side *caches* the other's counter and only re-reads on
  full/empty — shared-cache-line traffic drops from per-op to per-queue-depth.
- `alignas(64)` splits the counters onto separate cache lines: without
  this, the producer's tail writes invalidate the consumer's cached line
  (**false sharing**) — typically a 2-5x difference. This is THE canonical
  false-sharing demo; interviewers love it.

**Why SPSC per slot and not one MPMC queue:** multiple connection threads
are multiple producers; a correct lock-free MPMC queue is a genuinely hard
research-grade object (Michael-Scott queues need hazard pointers/epoch
reclamation). Per-session SPSC rings get the same benefit with a structure
you can actually prove correct on a whiteboard. Trading venues do exactly
this: one inbound queue per session gateway, one engine consuming.

**Where locks still exist (and why that's fine):** condvars *park* idle
threads (engine sleeps when no work; connection thread sleeps until its
response arrives). Signaling happens only on empty→non-empty transitions,
so under load neither side ever sleeps — steady state is pure atomics.
STATS shows the consequence: `core_lat` (queue+processing, includes the
condvar wake for sporadic commands) vs `proc_lat` (175ns p50, pure
pipeline). Spin-vs-park is a real trade-off; real engines busy-spin or use
eventfd.

**Slot handoff protocol (subtle, worth studying):** sessions are leased by
CAS on an `active` flag. Release = push `Disconnect` → engine cleans up →
sends `BYE` → client drains through BYE → clears the flag. Because the
client consumed *everything* up to and including BYE, both rings are
provably empty with consistent counters — so the next lease needs **no
counter resets**. One atomic flag is the whole ownership story. The
`core_slot_reuse` test leases/releases the same slot three times.

**Classic problems:** LC 622 (circular queue), the dining-philosophers /
producer-consumer family, and every "implement a thread-safe queue"
interview question — this file is the answer with the memory model done
properly.

### 4.9 Market-data feed (`cpp/gateway/md_publisher.{hpp,cpp}`, `py/md_client.py`)

**What it does.** After any submit/cancel that moves a symbol's best
bid/ask, the engine pushes an `MdUpdate{symbol, seq, bid, ask}` onto an SPSC
ring. The MD publisher thread drains it and fans text frames
(`MD sym=1 seq=5 bid=10000 ask=10050`) out to every TCP subscriber.

**Every design choice is a named concept:**
- **Engine never blocks on subscribers.** If the ring fills, the engine
  *drops* the update and counts it (`md_dropped`) — backpressure by
  subtraction. If a subscriber's socket clogs, it's disconnected. Both are
  the "slow consumer problem," and every real feed handler answers the same
  way: drop, never block the producer.
- **Sequence numbers per symbol.** A dropped frame is *detectable*: the
  client sees seq jump and knows it missed something.
- **SNAP + delta resync.** The client recovers by asking the gateway for a
  snapshot (`SNAP 1` → current top + current seq), then ignoring deltas at
  or before the snapshot's seq. This is exactly how FIX market-data
  recovery and every UDP feed handler's gap-fill works — the "cache
  invalidation" dance in miniature.
- **Fan-out** = the CDN shape: produce once, deliver to N consumers.

**Classic problems:** LC 1146 — Snapshot Array (versioned snapshots);
"design Twitter feed fan-out" (system design); "how would you make UDP
reliable" (exactly the seq + snapshot protocol here).

### 4.10 The market maker (`py/mm/mm.py`, `scripts/mm_demo.sh`)

**What it does.** A bot session that continuously quotes a bid and an ask
around a drifting "fundamental" price (a random walk standing in for real
signal — the honest simplification, stated in its docstring). Every 200ms:
poll `EVENTS` for maker fills → cancel both quotes → recompute → repost.
Inventory skews the quotes (long inventory ⇒ lower both sides ⇒ sell more
easily), which is textbook market making: earn the spread, bleed inventory.

**Why it matters for learning:** it exercises the entire stack from the
*client* side — the full protocol (AUTH/NEW/CXL/EVENTS), the fill
notification path (it's usually the maker, so its fills arrive via polling
EVENTS), cancel races (CXL returns UNKNOWN when the quote just filled —
handled), and PnL accounting (cash + inventory × mark price). Run
`scripts/mm_demo.sh`: the bot earns ~$90 in 14 seconds against two noise
traders, with inventory oscillating near zero.

**Classic problems:** LC 981 (time-series state), and the quant interview
staple: "you're a market maker, flow is 50/50 informed/uninformed — what's
your spread?" (adverse selection; this toy has none, and says so).

## 6. Worked example (real numbers from the smoke test)

```
AUTH dev-alpha-token                  → OK AUTH trader=alpha rate=100 ...
NEW 1 B 10 999500                     → RESTING   (bid: 10 @ $99.95)
NEW 2 S 10 1000500                    → RESTING   (ask: 10 @ $100.05)
NEW 3 B 5 1000500                     → FILLED [1000500x5]
   # buy crosses the ask: trades 5 @ maker's $100.05; maker 2 has 5 left
NEW 3 B 5 1000600                     → ERR DUPLICATE      (same ClOrdID)
NEW 4 B 99999 1000500                 → ERR RISK_QTY       (cap 5000)
EVENTS (from session of order 2)      → FILL cl=2 px=1000500 qty=5 remaining=5
STATS                                 → accepted=2 dup_rej=1 risk_rej=1 ...
```

Watch what the book did: order 3 swept the ask level, printed at the
maker's price, and left the maker half-alive (`remaining=5`) — that
partial-maker lifecycle (and notifying *its* session, not the taker's) is
most of the gateway's routing complexity.

## 7. Complexity summary (per order, hot path)

| Step | Cost |
|---|---|
| TCP recv + line split | syscall-dominated (~µs) |
| SPSC push + engine pickup | lock-free, ~µs incl. wake when idle |
| 5 gateway checks | hash probes + O(1) bucket + O(1) window ≈ ~100ns |
| Engine routing | O(1) hash |
| Book sweep + rest | O(log P + F), fixed memory |
| Response + SPSC pop | fixed buffers, no alloc |

Measured (same machine, `-O2`): engine alone **83ns p50** (8.7-11.6M
ops/s); engine-thread processing through the full gateway pipeline
**175ns p50 / 1.0µs p99** (`proc_lat` in STATS); round-trip through the
rings from 4 producer threads 7.4µs p50 (0.42M ops/s aggregate); full TCP
client RTT **86µs p50 / 135µs p99** under a 2000/s flood (mutex-era
baseline: 131µs / 201µs). The lesson in that ladder: **syscalls dominate,
then queue hops, then the algorithm** — which is exactly the argument for
kernel bypass, and why "optimize the data structure" is usually the *last*
thing that matters.

## 8. Exercises (each one is an interview rep)

1. **Add self-trade prevention**: reject/repurpose an order that would
   cross the same session's resting order. (Changes the sweep loop; think
   about which side to cancel.)
2. **Replace `std::map` with a sorted `vector` of levels** and benchmark —
   learn when O(log n) tree nodes lose to cache-friendly linear scan.
3. **Turn the dedupe set into a full LRU with TTL** (LC 146 with expiry).
4. **Add a second engine thread with a shard-split** (even/odd symbol IDs)
   and measure lock contention — then you'll *feel* why Phase 3 exists.
5. **Persist fills to SQLite from a worker thread** (Phase 3's async
   worker): the DS problem is a bounded multi-producer/single-consumer
   queue with a shutdown protocol.
6. **Write the SPSC ring buffer** (LC 622's concurrent big brother):
   head/tail atomics with acquire/release, 64-byte padding. This single
   file is the highest-value C++ interview artifact you can add.
7. **Market-data snapshot cache**: given a stream of book deltas with
   sequence numbers, serve consistent snapshots (LC 1146 Snapshot Array
   is the toy version).
